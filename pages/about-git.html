Зачем нужен Git и GitHub?

Добро пожаловать в ITHelper!

Всем салам алейкум, это гайд по понятию что такое GitHub, Git, ветки,pull request, merge, commit со студенческого взгляда. представьте следующее: Вы с друзьями( допустим вас 5 человек) собрались для того что бы сделать сайт-маркетплейс(что то вроде Wildberries).
Вы умеете писать код, кто то из вас берет на себя систему продавцов, кто то товаров, а кто то лучше разбирается в создании системы авторизации, однако возникает проблема- вы не умеете работать в команде. Представьте до чего ужасно работать целой командой за одним компьютером. Это крайне не эффективно и неудобно. Гораздо лучше работать каждому за своим ПК. так вы и делаете: каждый приобретает себе компьютер.
Но возникает еще одна проблема. файлы разработки(допустим у нас только 2 файла- index.html и styles.css) находятся на пк тимлида(Лидер команды) .И он передает вам архивированный файл с кодами по почте. Важно понимать что работая в команде, далеко не всегда каждый работает над своим не зависимым файлом, иногда один и тот же файл редактируется несколькими программистами. Это значит что условный файл index.html будет редактироваться несколькими вашими товарищами(к примеру 4 человека). И вот у нас сложилась следующая картина: тим лид создал у себя на пк 2 пустых файла(index.html и styles.css) он их упаковал в один архив и отправил вам всем по почте. 1 человек делает стили в файле .css, а 4 других добавляют свои функции в файл .html. Когда вы закончили, каждый из вас отправляет вами отредактированные файлы обратно тимлиду по почте. Какая картина перед тимлидом? он видет перед собой один файл .css и 4 разные версии файла .html(то есть ему на почту пришел 1 файл .css и 4 разных по содержанию но одинаковых по названию файла .html). вставить код новопришедшего файла .css в пустой оригинал не составит труда, а вот с .html дела иначе. тимлид должен взять с каждой версии только те отрывки кода которые выполняют конкретную функции и вставить их в пустой оригинал да еще и так что бы весь этот конструктивно собранный код слаженно работал. Это целое дело, которое очень сильно тормозит разработку. Именно для этого существуют Git и GitHub. GitHub это онлайн сервер куда тимлид может закинуть оригинал проекта, кстати, пространство в GitHub где находятся все файлы проекта называется репозиторием. А остальная команда получив ссылку на репозиторий может видеть его содержимое (файлы проекта). После того как тимлид загрузил проект в репозиторий GitHub, каждый участник команды больше не просит архивы по почте, ведь помимо того что команда видит то что в репозитории, каждый может загрузить копию на свой пк. И здесь нам впервый раз пригодиться Git.

Основные понятия

К этому моменту вы облегчили себе работу следующим образом: теперь вы видите актуальную версию основного проекта не используя почту. а также легко можете скачать репозиторий проекта себе на пк. Важно понимать одну вещь. Когда вы скачали проект, вы не работаете прямо на GitHub. Вы работаете с копией проекта у себя на компьютере. GitHub — это просто место, где хранится общая версия проекта. По этому что бы изменения отобразились в основном репозитории, их нужно отправить туда и это делается тоже благодаря команде в Git Bash. То есть Git можно представить как курьерскую службу которая отвозит ваш код в Git Hub и наоборот. и Вот вы все работаете намного быстрее. после того как кто то вносит изменения и их отправляет в репозиторий остальная команда сразу же может увидеть новую актуальную оригинальную версию проекта. Но появляется еще одна проблема. Тимлид замечает что некоторые разработчики вносят некачественные изменения и порой два разработчика редактируют один фрагмент кода. У него появилась потребность оценивать изменения перед тем как они попадут в основной проект. и что же им теперь, снова свои изменения отправлять по почте тимлиду? -нет. для этого у Git есть возможность создать ветки(Branches). то есть версии проекта. разработчик создает ветку. затем отправляет изменения не в основную версию (основная версия- это ветка main), а в свою ветку. И затем отправляет ветку на GitHub, делает заявку на рассмотрение (Pull Request) и теперь его ветка доступна для рассмотрения. Затем тимлид или же вы всей командой рассматриваете изменения. и если они вам нравятся то вы "Вливаете ветку в main " то есть соединяете. - этот процесс называется MERGE. Он происходит автоматически(почти, но об этом чуть позже) Раньше когда вы работали используя почту вы свои изменения кода комментировали либо в самом коде либо создавали новый файл с комментариями к изменениям. пример такой в оригинальной версии было: Добро пожаловать!
